# Buendia — MVP

> A hosted runtime for single-file HTML apps generated by AI assistants. Apps live on Buendia; app *data* lives in the user's own backend, which Buendia provisions and manages on their behalf.
>
> Read [CONSTITUTION.md](./CONSTITUTION.md) first. This document is the build plan; the constitution is the contract.

---

## Vision

Non-technical people produce real working applications by prompting Claude, ChatGPT, v0, Lovable, Bolt. The output is almost always a single HTML file. That file dies the moment they close the chat: no hosting, no persistence, no sharing, no upgrade path. The platforms that solve some of these problems solve them with lock-in: your app lives there, leaves never.

Buendia turns AI-generated HTML artifacts into living applications without absorbing them. Upload the file, the platform gives it a URL, provisions a database in the user's own backend, injects credentials at request time, and the app works — without the user ever seeing a SQL editor. The same HTML file, opened locally or hosted elsewhere, falls back to a setup screen that asks for credentials and works exactly the same way.

The product ships two ways from one codebase:

- **Hosted SaaS** — multi-tenant control plane, per-user managed-Supabase projects owned by users themselves.
- **Self-hosted open source** — `docker compose up`, the operator owns the data stack, schemas live there.

---

## What we are building, in one paragraph

A platform user signs up, connects their Supabase account (one OAuth click), drops an `index.html` and a `schema.sql` onto the dashboard, gets a URL, and shares that URL with two collaborators by email. The collaborators sign in to Buendia and see the same app, the same data, syncing live — all of it stored in the *owner's* Supabase project, not Buendia's. The owner removes one collaborator; their next click on the app fails. The owner disconnects Buendia from their Supabase account — the schema, the data, and the app keep working; Buendia simply stops being involved.

If we ship that, we have an MVP. Everything in this document either supports that paragraph or is post-MVP.

## Goals

1. A non-technical user uploads a `.html` file and within 60 seconds has a working URL with persistent data.
2. The HTML file is **portable**: it works on the platform, in `file://`, and on any static host (Constitution §1, §2).
3. The data lives in a backend the user owns directly (Constitution §3). Disconnecting Buendia does not move or break the data.
4. Apps can be shared with named people by email. Sharing is granted and revoked, not leaked (Constitution §4, §7).
5. The codebase deploys identically as multi-tenant SaaS and single-instance self-hosted (Constitution §5).
6. The platform is coupled to the open data-stack protocols, not to a vendor (Constitution §8).
7. **Project-tracker migrates to Buendia unchanged.** Same HTML, same realtime sync, same multi-collaborator UX, real auth instead of URL-paste-and-pray. This is the MVP's acceptance test.

## Non-goals (for MVP)

- Multi-file apps, bundlers, build steps. **Single HTML file only.** Inline JS/CSS and CDN ES module imports are fine.
- Server-side code uploaded by users.
- Custom domains. Subdomains under the platform domain (SaaS) or paths (self-hosted) only.
- Billing, plans, quotas.
- App marketplace, discovery, public gallery.
- Public read-only apps. Every app requires sign-in to access in MVP.
- AI-assisted schema generation in the dashboard.
- Mobile-optimised dashboard. Desktop first.
- Supporting "bare Postgres" backends without the rest of the data stack. Operators run Supabase OSS or compatible components.

## Target user

Two personas, deliberately:

- **The vibe coder.** Generates apps in Claude/v0/Bolt. Can edit HTML cautiously but won't write a Postgres migration. Wants to host the output and share it with their team. Pays for SaaS. Willing to OAuth Supabase once at signup if the rest is automatic.
- **The dev tinkerer** (you). Wants the OSS version because they want to run their own toolchain, audit the code, and not depend on a vendor. Doesn't pay, but is the marketing engine.

Build for the vibe coder; make the dev tinkerer feel respected (no magic they can't unwind).

## Core user flows

### First-time owner setup (SaaS)

1. Sign up to Buendia with email + password.
2. Buendia prompts: "To host your apps, connect your Supabase account. Don't have one? Create one free."
3. User OAuths with Supabase, granting Buendia permission to manage projects and users in their Supabase organization.
4. Buendia creates one project named "Buendia Apps" in the user's Supabase organization. Buendia fetches and stores (encrypted) the project's URL, anon key, service-role key, and JWT secret.
5. Provisioning takes 30–60 seconds. The dashboard shows a friendly "preparing your workspace" step. The user can fill in their profile while it runs.
6. Once ready, the dashboard's empty state shows the **Upload an app** CTA.

### Owner uploads an app

1. Drag in `index.html`. Optional: drag in `schema.sql` alongside.
2. Buendia runs the schema provisioner against the user's Supabase project: creates an `app_<slug>` schema, runs the DDL, adds `created_by uuid default auth.uid()` and `team_id uuid` columns to every table, generates default RLS policies.
3. App row written to Buendia's control plane with a generated slug.
4. Click **Open**. Buendia's edge route mints a JWT signed with the owner's project JWT secret, injects `<script>window.__APP_CONFIG__ = {...}</script>` before `</head>`, streams the HTML.
5. The SDK reads `__APP_CONFIG__`, constructs a client pointed at the owner's Supabase URL with the JWT pre-loaded, subscribes to realtime, exposes `Buendia.db`, `Buendia.user`, `Buendia.app`.

### Collaborator flow

1. Owner enters collaborator's email in the Share panel, picks role (viewer or editor).
2. Buendia writes a row to `app_shares`. Sends an invitation email with a sign-in link.
3. Collaborator clicks the link, signs up to Buendia (just email + password to Buendia's control plane — they do **not** need to connect their own Supabase; they're a guest in someone else's backend).
4. Dashboard's "Shared with me" tab shows the app.
5. Opening the app: Buendia's edge route mints a JWT signed with the *owner's* JWT secret, with the collaborator's user id as `sub` and their role in claims. The owner's Supabase accepts the JWT; RLS enforces what they can see.

### Revocation

1. Owner clicks Remove next to a collaborator.
2. Row deleted from `app_shares`, written to `audit_log`.
3. Next JWT mint for that user × app fails. Their existing JWT keeps working until `exp` (≤15 minutes); SDK refresh fails after that and shows a polite "access removed" message.

### Standalone flow

Same HTML opened from `file://` or any static host:

1. SDK boots, finds no `__APP_CONFIG__`.
2. SDK renders a setup overlay: "This app needs a Supabase project. Paste your project URL and anon key."
3. User pastes; SDK stores in `localStorage` under a namespaced key; app runs.
4. The setup overlay links to docs explaining how to spin up a free Supabase project and run the schema.

Standalone mode has no real auth — the SDK uses the anon key directly. That is a knowing degradation. The platform exists because URL-paste-and-pray is bad; if you opt out of the platform, you opt back into URL-paste-and-pray. This is documented.

### Disconnect

1. Owner clicks "Disconnect Buendia" in account settings.
2. Buendia shows what will happen: the user's Supabase project keeps running, their schemas keep their data, but Buendia will no longer serve their apps or manage sharing. Existing share grants become inert.
3. On confirm: Buendia zeros out the stored Supabase credentials, marks the user's apps as disconnected, removes them from the dashboard's serving routes. The owner can re-download each HTML + schema before disconnecting (export is in the same flow).

## Architecture

```
┌──────────────────────────────────────────────────────────────┐
│                    Buendia (monorepo)                        │
│                                                              │
│  apps/web        Next.js — dashboard, auth, upload, share UI │
│  apps/edge       Hono — serves user apps with injected config│
│  packages/sdk    @buendia/sdk — embedded in every user HTML  │
│  packages/shared TS types, zod schemas, constants            │
│  packages/db     Migrations, RLS policies, schema provisioner│
│                                                              │
└──────────────────────────────────────────────────────────────┘
            │                          │
            ▼                          ▼
   ┌──────────────────┐      ┌──────────────────────────────┐
   │Buendia Control DB│      │ Per-user Supabase projects   │
   │ (Buendia-managed)│      │ (user-owned, OAuth'd in)     │
   │                  │      │                              │
   │ users, apps,     │      │ Alice's "Buendia Apps":      │
   │ app_shares,      │      │   app_tracker.tracker_items  │
   │ owner_backends,  │      │   app_journal.entries        │
   │ audit_log        │      │                              │
   └──────────────────┘      │ Bob's "Buendia Apps":        │
                             │   app_recipes.recipes        │
                             └──────────────────────────────┘
```

The control plane is owned by Buendia. App data backends are owned by the users themselves (Constitution §3). They are never mixed.

### One backend project per user, schema-per-app within it

Each Buendia user gets one Supabase project (the "Buendia Apps" project, provisioned at signup) and each of their apps becomes a Postgres schema inside it. This balances three constraints:

- Free tier limit is 2 projects per Supabase organization. One project per Buendia-user fits.
- Supabase project creation takes 30–60s via the Management API. Doing it once at signup is acceptable; doing it per-app is not.
- Strong isolation between *users* (separate projects, separate JWT secrets) and reasonable isolation between *apps within a user* (separate schemas, RLS).

A premium SKU offering one project per app (for stronger isolation between apps owned by the same user) is post-MVP. The provisioner is behind an interface (`SchemaProvisioner` vs. a future `ProjectProvisioner`) so it ships without rewrites.

### Edge service

A Hono server (`apps/edge`) sits in front of user app subdomains. On each request:

1. Resolve subdomain (or path slug) → app id → owner id.
2. Verify the requester has a Buendia session cookie *and* is a member of `app_members` (owner, editor, or viewer).
3. Look up the owner's backend credentials in `owner_backends` (decrypt JWT secret).
4. Fetch the HTML blob from storage (cached aggressively).
5. Mint a short-lived JWT (≤15 min) signed with the owner's JWT secret, with the requester's user id and role.
6. Inject `<script>window.__APP_CONFIG__ = {...}</script>` before `</head>` with the owner's Supabase URL, anon key, and the freshly minted JWT.
7. Stream to client.

### Backend-agnostic at the protocol level

The SDK and edge service talk to the data stack via stable protocols: PostgREST for REST queries, the Realtime WebSocket protocol for live subscriptions, S3-style API for storage, signed JWTs with a documented claim shape for auth. The reference implementation is Supabase (managed in SaaS, OSS in self-hosted). Operators may substitute compatible components without touching Buendia's code.

For MVP, we ship coupled to the Supabase OSS client libraries (`@supabase/supabase-js`) because they are the most mature implementations of these protocols. The spec is decoupled even where the code is not. If a real operator emerges who wants to swap, say, the Realtime layer for Soketi, we add an interface then and not before.

## The SDK

`@buendia/sdk` is a single ESM module loaded via CDN from a `<script>` tag near the top of every user HTML:

```html
<script type="module">
  import { Buendia } from "https://cdn.buendia.app/sdk/v1/buendia.js";
  const platform = await Buendia.init();
  window.platform = platform;
</script>
```

### Surface

```ts
interface BuendiaClient {
  db: SupabaseClient;
  user: { id: string; email: string; displayName: string; role: 'owner'|'editor'|'viewer' };
  app:  { id: string; name: string };
  mode: 'hosted' | 'standalone';

  subscribe(table: string, callback: (event) => void): Unsubscribe;

  ui: { mountSetupOverlayIfNeeded(): void };
}
```

### Resolution order

1. `window.__APP_CONFIG__` — hosted mode.
2. `localStorage["buendia:<appId>:config"]` — standalone mode, previously configured.
3. Mount the setup overlay. Promise resolves once the user pastes credentials.

In all three cases the surface is identical. The app code does not branch on mode.

### Realtime is first-class

Project-tracker depends on realtime; so will most useful collaborative apps. The SDK must expose it, and the JWT minted by the edge service must include claims the Realtime service accepts for the app's schema.

```ts
platform.subscribe('todos', (event) => {
  // event.type: 'INSERT' | 'UPDATE' | 'DELETE'
});
```

Under the hood this is `supabase.channel(...)` with the schema pre-bound.

### JWT refresh

The SDK refreshes the JWT silently every 10 minutes via a Buendia control-plane endpoint (`POST /api/jwt/refresh?app=<id>`). If the refresh fails (because the share was revoked), the SDK shows a non-dismissable overlay: "Your access to this app was removed." This is the *only* code path that breaks under revocation; the UI itself stays mounted so the user sees a clear message rather than a silent error.

### Schema discovery

For MVP: user uploads `schema.sql` alongside the HTML. Buendia's schema provisioner:

1. Connects to the user's Supabase project using their stored service-role key.
2. Creates schema `app_<slug>`.
3. Runs the DDL, refusing any statement that disables RLS.
4. Adds `created_by uuid default auth.uid()` and `team_id uuid` columns to every table.
5. Generates default RLS policies (members read, editors+owner write).

## Data model (control plane)

```sql
create table users (
  id uuid primary key references auth.users(id),
  email text not null unique,
  display_name text,
  created_at timestamptz default now()
);

create table owner_backends (
  user_id uuid primary key references users(id),
  -- Encrypted using envelope encryption; key in KMS.
  supabase_project_ref text not null,
  supabase_url text not null,
  supabase_anon_key_encrypted bytea not null,
  supabase_service_key_encrypted bytea not null,
  supabase_jwt_secret_encrypted bytea not null,
  supabase_oauth_refresh_token_encrypted bytea not null,
  connected_at timestamptz default now(),
  last_validated_at timestamptz
);

create table apps (
  id uuid primary key default gen_random_uuid(),
  owner_id uuid not null references users(id),
  slug text not null unique,
  name text not null,
  schema_name text not null,
  team_id uuid not null default gen_random_uuid(),
  html_storage_path text not null,
  current_version int not null default 1,
  created_at timestamptz default now(),
  updated_at timestamptz default now(),
  unique (owner_id, schema_name)
);

create table app_versions (
  id uuid primary key default gen_random_uuid(),
  app_id uuid not null references apps(id) on delete cascade,
  version int not null,
  html_storage_path text not null,
  schema_sql text,
  created_at timestamptz default now(),
  unique (app_id, version)
);

create table app_shares (
  app_id uuid not null references apps(id) on delete cascade,
  user_id uuid not null references users(id) on delete cascade,
  role text not null check (role in ('viewer', 'editor')),
  invited_by uuid references users(id),
  granted_at timestamptz default now(),
  primary key (app_id, user_id)
);

create view app_members as
  select id as app_id, owner_id as user_id, 'owner'::text as role, team_id from apps
  union all
  select s.app_id, s.user_id, s.role, a.team_id
    from app_shares s join apps a on a.id = s.app_id;

create table audit_log (
  id bigserial primary key,
  actor_id uuid references users(id),
  action text not null,
  target_app_id uuid references apps(id),
  target_user_id uuid references users(id),
  metadata jsonb,
  created_at timestamptz default now()
);
```

The new piece compared to the previous draft is `owner_backends`: one row per Buendia user, holding the encrypted credentials needed to act on their Supabase project. This is the most security-sensitive table in the system.

### Credential storage

- Envelope encryption: each row is encrypted with a per-row data key; the data key is encrypted with a KMS key (AWS KMS, GCP KMS, or HashiCorp Vault in self-hosted).
- The service role key and JWT secret are only ever decrypted in the edge service or schema provisioner, never logged, never sent to the browser.
- Periodic re-validation: a daily job tries `Buendia.health()` against each owner's project to catch revoked OAuth grants before the user hits an error.

## Auth & isolation

- Control-plane auth: Supabase Auth on Buendia's own Supabase. Email + password for MVP.
- App-data auth: JWTs signed with each owner's Supabase project JWT secret. The owner's Supabase accepts these natively — it doesn't need to know the user exists in its `auth.users` table; the JWT just has to be signed correctly.
- JWT claims:

  ```json
  {
    "sub": "<buendia_user_id>",
    "role": "authenticated",
    "app_id": "<uuid>",
    "app_schema": "app_<slug>",
    "team_id": "<uuid>",
    "buendia_role": "owner|editor|viewer",
    "exp": <now + 15min>
  }
  ```

- Default RLS policies, generated by the provisioner for every user table:

  ```sql
  create policy "members read"  on app_xxx.foo for select
    using (team_id = (auth.jwt() ->> 'team_id')::uuid);
  create policy "editors write" on app_xxx.foo for all
    using (
      team_id = (auth.jwt() ->> 'team_id')::uuid
      and (auth.jwt() ->> 'buendia_role') in ('owner','editor')
    )
    with check (team_id = (auth.jwt() ->> 'team_id')::uuid);
  ```

- The PostgREST `Accept-Profile` header is set by the SDK to the app's schema, so only that schema is reachable from this app.

## Hosted vs self-hosted

Both ship from the same repo. Differences:

| Concern         | Hosted SaaS                            | Self-hosted                          |
|-----------------|----------------------------------------|--------------------------------------|
| Control plane   | Buendia-managed Supabase               | Local Supabase via `docker compose`  |
| App data        | User's own Supabase project (OAuth'd)  | Operator's data stack (Supabase OSS or compatible) |
| Backend connect | Supabase OAuth flow at signup          | Operator pre-configures credentials in env file |
| Auth (control)  | Supabase Auth, email/password          | Same                                 |
| Subdomains      | Wildcard DNS, Cloudflare in front      | Path-based: `host/a/<slug>`          |
| Billing         | Stripe (post-MVP)                      | n/a                                  |
| Email           | Resend                                 | Local SMTP or "copy this link"       |
| Credential storage | KMS-backed envelope encryption      | Local KMS-equivalent (e.g. age, Vault) |

In self-hosted mode there is no per-user OAuth flow — there is one data stack, configured once by the operator, shared by all users on that instance. The `owner_backends` table still exists but is populated identically for every user (pointing at the local stack).

## Tech stack

- **Monorepo**: pnpm workspaces + Turborepo. Node pinned via Volta.
- **Frontend** (`apps/web`): Next.js 15 (App Router), TypeScript strict, Tailwind, shadcn/ui.
- **Edge** (`apps/edge`): Hono on Node. For the smallest-viable deployment, this could be collapsed into Next.js API routes; revisit if scaling profiles diverge.
- **SDK** (`packages/sdk`): Pure TypeScript, no React. Compiled to ESM and IIFE. Published to npm *and* served from `cdn.buendia.app/sdk/v1/buendia.js`.
- **Data stack client**: `@supabase/supabase-js` (talks to PostgREST + Realtime + Auth + Storage).
- **Management**: `@supabase/management-js` for Supabase OAuth and project creation in SaaS mode.
- **Crypto**: `node:crypto` for envelope encryption; AWS KMS / GCP KMS / Vault for key wrapping.
- **Hosting**: Vercel for `apps/web` in SaaS mode; `docker compose` for self-hosted.

## Phasing

### Phase 0 — Skeleton (1 week)
- Monorepo scaffolding, CI, deploy `apps/web` to Vercel.
- Buendia control-plane Supabase Auth: signup, signin, session middleware.
- Empty dashboard with "no apps yet" empty state.

### Phase 1 — Supabase OAuth + project provisioning (1–2 weeks)
- Supabase OAuth flow at signup.
- Management API integration: create the user's "Buendia Apps" project, fetch credentials, store encrypted.
- Provisioning UI: "preparing your workspace" with the 30–60s wait absorbed cleanly.
- Account settings page that shows the connected project.

### Phase 2 — Upload + serve (1–2 weeks)
- Upload `.html` + `schema.sql`. Store HTML in Supabase Storage.
- Schema provisioner: connects to user's Supabase using stored credentials, creates `app_<slug>` schema, runs DDL, adds standard columns, generates RLS.
- Serve route at `/a/<slug>` that fetches HTML, mints JWT signed with owner's JWT secret, injects `__APP_CONFIG__`.
- SDK v1: resolves config, exposes `Buendia.db`, `Buendia.user`, `Buendia.app`, `Buendia.subscribe`.
- Realtime works end-to-end against the owner's Supabase.

### Phase 3 — Sharing (1–2 weeks)
- Share UI: invite by email, list members, remove.
- Invitation email with a magic sign-in link to Buendia.
- "Shared with me" tab.
- JWT minter resolves the right owner's JWT secret based on the app being accessed.
- Revocation immediate (JWT TTL ≤15 min).

### Phase 4 — Project-tracker canary (1 week)
- Migrate `luisgrandegg/project-tracker` to Buendia. Replace its inline Supabase setup with the SDK.
- End-to-end test with two real users (you and your partner). Realtime, sharing, revocation, disconnect.
- This is the MVP acceptance test.

### Phase 5 — Polish (1–2 weeks)
- App rename, delete, re-upload with versioning.
- Storage usage display.
- Export: one click downloads `index.html`, `schema.sql`, and a SQL dump from the user's Supabase.
- Disconnect flow.
- Landing page.
- Self-hosted `docker compose` recipe, smoke-tested.

**~9–11 weeks to MVP.** The OAuth + provisioning phase is the meaningful new work; everything else is similar to the prior plan.

## Open questions

1. **Schema declaration UX.** Worth a 1-hour spike to see what Claude/v0/Bolt produce when asked for "an app with persistence". If their schemas are coherent, MVP `schema.sql` is fine.
2. **Subdomain vs path routing in SaaS.** Subdomains need wildcard TLS + Vercel Pro. **Lean: path-based in MVP, subdomains as a Phase 5 polish if it's cheap.**
3. **Storage limits per app.** Need a default. 100MB? 1GB? (This affects the *owner's* Supabase quota, not Buendia's, which simplifies the conversation.)
4. **CSP for app subdomains.** Apps load CDN resources. Need a sane default that doesn't break common patterns.
5. **OAuth grant revocation handling.** If the user revokes Buendia's access in Supabase's dashboard, every operation Buendia tries on their behalf will fail. The daily validation job catches this; the UI surfaces it. What does the user-facing recovery look like — re-OAuth and resume, or treat it as terminal disconnect?
6. **Key rotation.** If a user's Supabase JWT secret rotates (manual action on their part), every JWT we mint will be rejected. We need a "refresh credentials" button that re-fetches via the OAuth grant. Cheap, but needs to exist.
